1. THE BIG PICTURE: WHAT A WEB INSTRUMENT ACTUALLY IS
==============================================================================

An audience member's journey:

  1. They scan a QR code with their phone camera.
  2. The QR code contains a URL
     (https://<username>.github.io/a-score-for-all-of-us/).
  3. The phone's browser opens that URL and downloads a web page.
  4. The web page contains code (JavaScript) that runs ON THE PHONE.
  5. They tap "Start" (browsers require a tap before any sound can play).
  6. They tap, hold, or tilt the phone, and sound happens.

Code that runs inside a phone's browser must be JavaScript. Python is used
on YOUR computer only: a local test server and QR code generation. The
instrument itself = HTML + CSS + JavaScript.

What you already bring:
  - p5.js experience: p5.js IS JavaScript.
  - COMS W3157: command line, Git, Make, separate compilation, pointers,
    structs, debugging discipline. See Section 3 for how these transfer.

The browser's built-in sound engine is the Web Audio API. Tone.js sits on
top of it and gives you musical concepts (synths, notes, envelopes,
effects) instead of raw signal plumbing.

2. ARCHITECTURE: WHAT WE BUILD, AND IN WHICH VERSION
==============================================================================

v1.0 — ARCHITECTURE A, "every phone is an instrument"   (due Nov 9)
------------------------------------------------------------------
  Each phone does everything itself: screen + sound. No server.

    [phone] --plays sound itself
    [phone] --plays sound itself
    [phone] --plays sound itself

  Hosting: GitHub Pages (free, HTTPS, permanent URL).
  Section changes: DEMO MODE. The person holding the phone advances
  sections with an on-screen control. This is exactly what an application
  reviewer needs, because there is no conductor when they try it.

v1.1 — ARCHITECTURE C, A + a "conductor" layer           (by Nov 30)
------------------------------------------------------------------
  Same instrument, plus a conductor page that only you (or a performer)
  open. Pressing "Section 2" there sends a small message through a
  real-time relay, and every audience phone switches its screen cue and
  sound set.

    [conductor page] --"section 2"--> [real-time relay] --> [all phones]

  Sound still comes from each phone. Only the section number travels over
  the network. Demo mode stays available for the online version.

  The choice of relay (a hosted real-time service vs. a small server you
  run) is decided at the start of Phase 7, not now.

THE ONE DESIGN RULE THAT CONNECTS v1.0 AND v1.1
-----------------------------------------------
  All section changes go through ONE function, for example
  setSection(n). In v1.0, the on-screen control calls it. In v1.1, a
  message from the conductor calls it. The rest of the code never changes
  section any other way. If you follow this rule, v1.1 is an addition,
  not a rewrite.

Compositional note: phones are not synchronized with each other, and phone
speakers are small and thin next to eight strings. Both are compositional
constraints of the genre, and many pieces use them deliberately (clouds,
textures, spatial distribution, entrances by seating area).

  ----------------  ---------------------------  -----------------------------
  Page structure    HTML                         Required by every browser

WHERE TO WORK
  Work on YOUR OWN LAPTOP:
  - You must open the page in a browser on the same machine to hear it.
  - Your GitHub credentials and pushes belong on your own machine.
  (macOS includes vim. On Windows, use WSL.)

DAILY SETUP (three terminal tabs or tmux panes + one browser window)

  tab 1:   vim js/sounds.js                 editing
  tab 2:   python3 -m http.server 8000      local server; leave running
  tab 3:   git status / add / commit / push
  browser: http://localhost:8000 with the developer console open

  The cycle: edit -> save -> refresh browser -> read console. There is no
  compile step.

.vimrc ADDITIONS FOR WEB FILES (web convention is 2-space indentation)

  syntax on
  filetype plugin indent on
  autocmd FileType html,css,javascript setlocal tabstop=2 shiftwidth=2 expandtab

HOW COMS W3157 TRANSFERS

  3157 concept                   In this project
  -----------------------------  ---------------------------------------------
  CLI, Git, lab workflow         Same workflow; commit small and often
  Separate compilation, headers  Split code into modules (main.js,
                                 sounds.js, ui.js) with import / export
  Pointers, structs, heap        Mental model for JavaScript objects and
                                 references (two names, one synth object)
  gdb / valgrind / test drivers  Browser developer console; test checklist

  New concepts you will learn here (we cover each explicitly):
  1. Event-driven programming: the page sets things up, then WAITS for
     events ("when tapped, do X"; "when tilted, do Y"). A C program runs
     main() top to bottom; a web page mostly reacts.
  2. The browser: HTML elements, the page structure (DOM), permissions
     for audio and motion sensors.
  3. JavaScript syntax: closer to C than to Python.

12. HOW WE WORK TOGETHER (KEEPING THE CODE GENUINELY YOURS)
==============================================================================

  My role (tutor/co-worker): explain concepts, propose structure, point to
  documentation, review code you wrote, help debug by asking questions and
  explaining error messages, check documentation for clarity.

  Your role: make every design decision, type every line of code that
  ships, write all prose under your name (README, DEVLOG, statements).

  Working protocol, per task:
    1. You state the goal in one sentence ("Tapping plays a random note
       from a scale").
    2. I explain the concept and the relevant API, and give a small
       illustrative example that is NOT your project code (different
       sounds, different structure), or pseudocode.
    3. You write your version yourself, in Vim.
    4. You run it. If it breaks, paste the error and your code; I explain
       the cause, you make the fix.
    5. You commit with your own message and write 2-3 lines in DEVLOG.md.
    6. Self-check before moving on: could you rewrite this function from
       scratch tomorrow without looking? If not, we review it again.

  Disclosure: read each program's policy on AI tools. A short honest line
  in the README acknowledgments (that you used an AI assistant as a tutor
  for learning JavaScript/Web Audio and for debugging explanations) is
  standard, and protects you.
